## 2. What changed, in one screen

- **Compiler 0.2.0 / manifest v2.** Items may share pages through `atlasGroup`; images are deduplicated across the
  whole build; every frame is validated before anything is packed or written. Linear pages are packed mip-safe:
  images start on 2^L boundaries with ≥ 2^L transparent texels around them (L = 3 by default). Fixtures: 12 pages
  (was 13), 6.06 MiB level 0 (was 4.58 MiB), 8.08 MiB with mip chains, 339 KiB of PNG.
- **Decode / upload.** `fetch` + `createImageBitmap` (premultiplied, flipped, no colour conversion) off the main
  thread; at most 2 uploads per frame between frames; mip chains generated by GL and clamped to the safe levels.
- **Registry v2.** `UNRESOLVED → REQUESTED → FETCHING → DECODED → UPLOAD_QUEUED → RESIDENT` (+ `RETRY_BACKOFF`,
  `FAILED`, `EVICTED`); pins from visible characters; budget with LRU eviction down to a low watermark; one
  opportunistic prefetch per culled character; abortable, capped, deduplicated fetches; exponential backoff for
  transient errors only; generation-checked handles; context-loss recovery from decoded copies.
- **Renderer.** Binds pages through handles, re-binds on every registry revision, hides any layer whose handle
  went stale, and ranks transparent world objects with the characters. Steady-state frames make no registry calls.
- **Tools.** `bench:baseline` reads the v2 registry stats and takes `--query`; new `bench:stages` times each
  stage of a frame in isolation (optionally A/B against another build); `mips=0` and `budgetMiB=` URL parameters.

## 4. Performance against Milestone 0

Details, raw files and methodology: [`benchmark-results/m2/2026-10-09/README.md`](benchmark-results/m2/2026-10-09/README.md).

All figures: headless Chromium 141 + SwiftShader, 4-core container, CPU time per frame on the main thread.

| Full frame loop, p50 (interleaved runs) | M0 `3db7a20` | M2 final `2836d80` | M2 final, `mips=0` |
|---|---:|---:|---:|
| 100 characters | 4.05 ms (3.69–4.19) | 4.17 ms (3.83–4.49) | 4.50 ms (4.16–4.77) |
| 300 characters | 13.87 ms (12.54–14.38) | 13.68 ms (13.56–14.36) | 13.47 ms (12.92–13.83) |

- **No measurable regression in the full loop** once the per-frame residency bookkeeping was fixed (`2836d80`).
  Before the fix, `prepareFrame` cost +64 % at 300 characters (isolated); now it is 3–11 % *below* M0 at 20–300.
- The first M2 run seemed 27–63 % slower than the M0 baseline, but part of that was the machine: the unchanged M0
  build re-measured 18–33 % slower in the same session. Only same-session comparisons are used now (ADR-10).
- **Open item:** in isolation `three.render()` takes 6–24 % longer at 100–300 characters, with or without mips; a
  CPU profile puts the extra time in JavaScript, not in WebGL calls. It does not show in the full loop.
- **Mipmaps:** about 6–9 % more SwiftShader raster time at 100–300 characters and 8.08 instead of 6.06 MiB of
  estimated GPU memory; no CPU effect measured. Their GPU cost is unknown until the checklist run.
- **Loading:** 12 page requests instead of 13 (`core` group), 356 KiB downloaded (was 354); time to ready at 300
  characters 693 ms vs 478 ms, because uploads are capped at 2 per frame and SwiftShader frames are slow.

## 5. Known limitations

- **No GPU numbers yet.** Every timing here is SwiftShader in a 4-core container. Mipmapped (trilinear) sampling is
  CPU work there; on a GPU its cost is expected to be small, but that is unmeasured until the checklist run.
- **Memory cost of mip safety:** for the fixtures, alignment and gutters add 32 % to level-0 page bytes and the
  chains bring the total to 1.76× M0's pages. Lower `mipLevels` per item, better packing or KTX2 can reduce it.
- **Mip correctness is verified for box-filtered chains** (a CPU simulation of what `generateMipmap` does on common
  drivers), not by reading back GPU mip levels; a driver with a wider downsampling kernel could reach further than
  the gutter at the deepest levels. A GPU readback test is a follow-up.
- **Atlas groups are declared by hand** (`core` in the fixtures). Packing groups from co-use statistics is not done.
- **PNG only:** no KTX2/Basis transcoding yet (planned after PNG parity, as the blueprint requires).
- **Upload throttling** (2 pages per frame) lengthens time-to-ready when frames are slow; a time budget per frame
  would adapt better.
- **Stale handles never reach `resolve()` in the browser runs** (the renderer re-binds first), so the stale path is
  exercised by unit tests only, including a simulated registry bug.
- **No hot manifest patching:** a new manifest version needs a reload. **One budget number** for every device; byte
  figures are estimates, not measured VRAM. `beginFrame` scans all pages each frame (fine for 12 pages).
- **Prefetch is frustum-based only** (no movement or zone prediction).
